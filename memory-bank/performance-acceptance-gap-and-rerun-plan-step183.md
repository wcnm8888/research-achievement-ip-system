## 认证后复跑前置条件

认证后复跑只能在本地评审 / 本地 Docker production-like 范围内执行，且需要人工现场提供临时本地账号：

1. 由人工现场创建或确认一个临时本地测试账号。
2. 人工在运行终端临时注入 `LOCAL_PERF_EMAIL` 和 `LOCAL_PERF_PASSWORD`。
3. Codex 不读取、不打印、不保存、不提交密码值。
4. Codex 不读取浏览器 Cookie，不读取 Token，不复述 session 内容。
5. 脚本只在内存中使用登录返回的本地 session cookie 发起后续请求。
6. 结果只记录聚合指标，例如状态码集合、请求数、失败数、`p50`、`p95`、`max`、是否超过阈值。
7. 复跑结束后由人工清理终端环境变量或关闭当前终端会话。
8. 产物目录 `.local-step170d-performance/` 作为本地运行产物，不提交。

认证后复跑的成功口径只能是“本地认证后短时性能基线已复跑”，不能说成“生产性能验收已完成”。

## 正式 10000 条检索验收方案

### 数据准备

- 准备至少 10000 条成果记录，覆盖论文、专利、软著等主要成果类型。
- 数据应包含标题、摘要、关键词、作者 / 贡献者、部门、状态、涉密标记、归档状态等常用检索字段。
- 数据应区分普通数据、部门隔离数据、涉密授权数据和不可见数据，验证权限过滤成本。
- 使用可回滚、可追踪的数据准备方案，避免污染真实生产数据。

### 索引准备

- 明确当前全文检索实现、数据库索引、组合索引和排序字段。
- 在验收前执行索引状态检查，确认索引存在、统计信息更新、查询计划合理。
- 对常见关键词、空结果、宽泛关键词、高命中关键词分别确认查询计划。
- 记录索引版本、迁移版本、数据库版本和数据规模。

### 权限过滤准备

- 准备至少三类身份：普通科研人员、部门管理员、系统管理员。
- 验证部门隔离、涉密授权、成果状态、归档状态对查询结果和响应时间的影响。
- 查询结果必须同时满足性能指标和权限正确性，不能为了性能绕过权限过滤。

### 查询集设计

- 热门关键词：命中量较高，验证排序、分页和摘要返回。
- 精确关键词：命中量中等，验证常规检索路径。
- 冷门关键词：命中量低或空结果，验证无结果响应。
- 多条件组合：关键词 + 类型 + 状态 + 部门 + 费用状态等。
- 权限敏感查询：同一关键词在不同角色下返回不同可见范围。
- 分页查询：第一页、靠后页和不同 `take` 数量。

### 指标

| 指标 | 建议验收口径 |
| --- | --- |
| 平均响应 | 10000 条成果数据规模下，核心查询集平均响应小于等于 1 秒 |
| `p95` | 明确记录，建议作为正式验收硬指标或预警指标 |
| `p99` | 明确记录，用于识别长尾慢请求 |
| 错误率 | 正式窗口内 HTTP 5xx / 网络失败 / 超时应低于约定阈值 |
| 正确性 | 权限过滤、分页、排序和结果字段正确 |
| 吞吐 | 记录每秒请求数或每分钟请求数，辅助容量评估 |

### 监控

- 应用：请求延迟分位数、错误率、吞吐、应用日志、异常堆栈。
- CPU：平均值、峰值、持续高位时间。
- 内存：RSS / heap、峰值、是否有持续增长。
- 数据库：连接数、慢查询、锁等待、缓存命中率、查询计划。
- 容器 / 主机：CPU throttling、磁盘 I/O、网络 I/O。
- 日志：慢查询日志、应用错误日志、认证失败或权限异常日志。

### 停止条件

- 发现权限绕过、数据泄露或越权返回。
- 错误率超过验收阈值并持续出现。
- `p95` / `p99` 长时间显著超出目标。
- CPU、内存、数据库连接或锁等待达到危险区间。
- 应用崩溃、容器重启、数据库连接耗尽或日志持续报错。

## 正式 50 用户并发验收方案

### 场景选择

正式 50 用户并发应覆盖真实业务操作，而不只是单一 GET 检索：

- 登录后查看工作台 / 待办。
- 成果台账列表、详情和筛选。
- 全文检索和高级筛选。
- 成果创建草稿、保存、提交。
- 审批待办查看和处理。
- 费用台账查看和提醒。
- 自定义报表模板列表和报表预览。
- 审计日志查询。

### 读写比例

建议采用以读为主、少量写入的评审场景：

- 读操作：约 80% 到 90%，包括列表、详情、检索、看板、报表、审计查询。
- 写操作：约 10% 到 20%，包括创建草稿、提交、审批、状态更新等。
- 写操作必须使用隔离测试数据，避免污染正式业务数据。

### 并发阶段

| 阶段 | 建议 |
| --- | --- |
| ramp-up | 逐步从 1、5、10、25 增加到 50 并发，观察系统曲线 |
| steady | 保持 50 并发稳定窗口，记录延迟、错误率、吞吐和资源指标 |
| ramp-down | 逐步降载，观察连接释放、队列清空和资源回落 |

### 停止条件

- 应用崩溃、容器重启、数据库连接耗尽。
- 错误率超过约定阈值并持续无法恢复。
- 关键业务流程出现错误状态、重复提交或数据不一致。
- 数据库锁等待、慢查询或 CPU / 内存高位持续扩大。
- 日志出现权限、认证、数据完整性或异常堆栈问题。

### 错误率阈值

- HTTP 5xx、网络失败、超时、脚本级失败应单独统计。
- 业务校验失败和预期 401 / 403 不应混入系统错误率，但需单独列明。
- 建议在正式方案中明确总错误率阈值、关键接口错误率阈值和中止阈值。

### 业务数据隔离

- 使用专用测试租户 / 部门 / 用户 / 数据前缀。
- 写入数据可追踪、可审计、可回滚。
- 不使用真实个人隐私、真实生产凭证或真实外部系统。
- 压测前后记录数据快照、清理方案和人工确认点。

## 演示问答口径

### 是否已完成 10000 条检索小于等于 1 秒？

没有正式完成。当前已有本地性能基线脚本和检索接口短时 GET 基线能力，但 10000 条成果数据规模、权限过滤、索引状态、监控指标和正式报告还没有形成验收闭环。可以说这是上线前 / 生产化专项必须复跑的性能验收项。

### 是否已完成 50 用户并发？

没有正式完成。当前脚本包含检索接口 50 并发轻量预演能力，但它不是 50 个真实用户的登录后业务操作验收，也没有覆盖读写混合、ramp-up、steady、ramp-down、错误率阈值和业务数据隔离。

### 现在性能证据是什么？

现在的证据是：已有 `scripts/local-performance-baseline-step170d.mjs` 本地性能基线脚本，支持本地认证参数，支持本地短时 GET 基线和检索接口 50 并发轻量预演口径。Step174 和 Step180 已明确不能把这些证据说成生产性能验收完成。

### 为什么不现场压测？

本次是文档收口，不是压测执行。现场压测需要明确数据规模、临时本地账号、测试窗口、监控指标、停止条件和数据隔离方案；否则容易产生不可解释的结果，也可能影响演示环境稳定性。当前不读取账号密码、Cookie、Token，也不访问生产环境或生产监控平台。

### 上线前还需要什么？

上线前至少需要：准备 10000 条成果数据和索引检查，设计权限过滤查询集，执行认证后业务接口复跑，完成 50 用户并发读写混合场景，接入 CPU、内存、数据库、慢查询、应用日志等监控，形成正式性能报告、瓶颈分析、容量评估和遗留风险清单。
