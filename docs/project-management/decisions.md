# 项目决策记录

更新时间：2026-07-25

## D001：长期资产与阶段档案分层

方法论工作区、当前项目仓库、阶段归档和 `docs/tests` 长期资产分开管理。历史提示词、一次性日志、原始浏览器痕迹和临时构建产物不作为当前架构依据。

## D002：阶段二采用最小质量修复与可审查提交

只修复过期测试断言、真实未使用变量和脚本 ESLint 环境边界；Git 整理按主题拆分提交，并在提交前执行测试、typecheck、build、lint 和差异检查。

## D003：当前源码、测试和最新 Git 基线优先

当历史 Step 文档、旧目录说明与当前实现冲突时，以当前源码、Schema、测试结果和最新 Git 提交为准。历史材料只保留必要背景，不继续作为当前状态或架构结论。

## D004：阶段三 Step 1 只刷新权威文档

本 Step 不通过文档更新顺手修改代码、测试、配置或 Schema，不执行生产和真实外部系统操作，不提交和推送。原先把下一步指向浏览器视觉基线的表述已由 D006 纠正。

## D005：Git/GitHub 交付只认一份全局标准

本项目所有 Git、提交、推送、PR、合并和发布动作统一遵循 `E:\Vibe coding\vibe-methodology\07-git-delivery.md`。项目内只记录当前分支、提交、门禁、例外和证据，不再维护第二套重复的 GitHub 推送规则。CI、分支保护、PR 和生产发布仍需单独授权。

## D006：UI 设计必须先于 UI 实现和视觉验收

后续 UI 工作统一遵循 `E:\Vibe coding\vibe-methodology\05-ui-design-system.md`：先审美与参考、再 UX 和信息架构、再 Style/Design System、再核心页面规格、人工确认、实现和浏览器验收。此前阶段三 Step 2 的浏览器检查只作为 UI 现状摸底，不作为正式设计基线通过。

## D007：六阶段整改路线与产品价值切片

- 决定：后续整改统一按“产品定义 → 架构与 UI 定向 → 工程基线 → 用户价值切片迭代 → 发布验收 → 复盘归档”推进。
- 原因：原有流程按大量技术 Step 和聊天输出递归，导致上下文放大、职责混杂和阶段无法结束；六阶段路线把长期产物、门禁和人工确认点固定下来。
- 执行规则：一个功能只维护一张任务卡，一个分支对应一张任务卡；任务结束更新短进度和证据摘要，不把 Prompt 历史作为长期项目记录。
- 当前映射：阶段一、阶段二和阶段三 Step 0/Step 1 已完成；阶段三 Step 2 完成 UI 设计基线，GitHub Actions、PR 模板和首个垂直切片任务卡已进入工程基线分支，分支保护和远程 CI 验证仍待完成。

## D008：阶段三 Step 2 的 UI 基线方向

- 决定：推荐采用“冷静的科研档案工作台”方向，先以 UX、状态、权限和数据密度为设计约束，再确定实现细节。
- 原因：系统是内部科研成果管理工作台，主要任务是登记、审批、检索、费用和审计，不适合营销化或装饰性视觉；该方向也能复用当前蓝青色 token 和现有 Ant Design 组件基础。
- 历史待确认项：最终视觉方向、Token 起点、字体候选和五个核心界面优先级在本记录形成时尚未批准，现已由 D015 取代并完成用户确认。

## D009：项目长期文档边界

- 决定：`README.md`、`AGENTS.md` 和 `docs/` 是当前项目长期事实文档入口；`docs/operations/` 属于长期运行、安全、备份、恢复和生产就绪资产。
- 原因：运行手册虽然包含生产和历史阶段编号，但它们承担可复用的安全与操作边界，不能与 Prompt 历史、完整日志或临时浏览器产物混为一类。
- 规则：阶段归档只用于追溯和交接，Prompt 历史和原始过程材料不作为当前架构、需求、路线或任务权威来源。

## D010：数据模型与安全模型暂不拆分为重复权威

- 决定：当前继续以 `docs/architecture/architecture.md` 中的数据模型概览、认证授权和访问边界章节作为当前事实来源。
- 原因：现有架构文档已覆盖这些内容；本阶段直接创建 `data-model.md` 和 `security-model.md` 会形成双权威和同步成本。
- 后续：在阶段六架构专项评审中，如果数据模型或安全模型的复杂度已经需要独立维护，再建立独立文件并同步迁移规则。

## D011：当前任务和路线入口

- 决定：使用 `docs/project-management/roadmap.md` 记录项目级路线，使用 `docs/project-management/current-task.md` 记录唯一当前任务。
- 原因：避免 `implementation-plan.md`、`progress.md`、聊天历史和 Prompt 历史同时承担下一步决策职责。
- 当前状态：第四阶段收口已完成，`current-task.md` 已建立首个垂直切片任务卡；功能实现仍等待工程基线 PR 的远程 CI 验证。

## D012：方法论采用唯一入口和职责单一化

- 决定：`E:\Vibe coding\vibe-methodology\README.md` 作为唯一索引入口，`02-methodology-router.md` 作为唯一任务路由；M/L 功能实现前必须建立 `03-task-card.md` 任务卡。
- 决定：测试选择统一使用 `06-test-selection-matrix.md`，上下文和 Token 预算统一使用 `08-context-and-token-budget.md`。
- 决定：继续保留 `07-git-delivery.md`、`05-ui-design-system.md` 和 `12-阶段复盘与归档.md` 分别作为 Git/GitHub、UI、复盘归档的唯一规范，不新增同义的 `07-git`、`05-ui` 或 `09-retrospective` 文档。
- 原因：此前任务方向依赖聊天输出和重复 Step 文档，导致上下文放大、职责混杂和测试自证；职责单一的入口能让后续任务只读取必要内容，并把下一步锁定到已确认路线和验收标准。
- 当前状态：第五阶段方法论入口已形成并映射到本项目；GitHub Actions、PR 门禁和首个垂直切片任务卡已进入工程基线分支，远程 CI 验证待 PR 触发。

## D013：阶段六架构基线最终评审

- 决定：当前继续采用模块化单体、Web/API/Shared/Prisma 分层、Guard/Policy 授权边界和适配器隔离作为架构基线。
- 决定：数据模型和安全模型继续作为 `architecture.md` 的章节维护，不在当前阶段拆成第二套权威文档。
- 决定：`App.tsx` 的 `activeKey` 页面入口、正式路由、深链接、浏览器返回、API 状态管理、缓存和重试策略分别列为后续架构决策，不在本阶段修改代码。
- 原因：源码与现有架构文档已经能够相互解释；当前缺口属于需要独立取舍和验收的架构问题，直接实现会扩大本阶段范围。

## D014：阶段六 UI 基线评审结果

- 决定：当前 UI 设计规格作为后续浏览器验收的文档基线，覆盖应用外壳、13 个导航入口、状态模式、响应式行为、安全展示边界和五个核心页面。
- 保留待确认：视觉方向“冷静的科研档案工作台”、蓝青 Token 起点、`Source Sans 3` + `IBM Plex Mono` 字体候选、五个核心页面优先级。
- 规则：方向已确认，但仍不进行无任务卡的大规模 UI 重构，也不把设计文档存在或截图生成写成视觉验收通过。
- 原因：AI UI 方法要求先完成参考、UX、Style/Design System 和页面规格，再由用户确认方向，最后进行浏览器验收；当前已完成前两步，浏览器验收仍需真实环境和可复现证据。

## D015：用户确认一期 UI 基线

- 决定：一期采用“冷静的科研档案工作台”视觉方向，当前蓝青色 Token 作为起点，`Source Sans 3` + `IBM Plex Mono` 作为字体候选，核心页面按“工作台 → 成果列表 → 成果详情/编辑 → 审批任务 → 系统配置”推进。

## D017：首个垂直切片使用本地 staging API 做真实数据库验收

- 决定：浏览器验收继续访问现有 Web 容器，但通过 Playwright 路由将本次 `/api` 请求发送到临时 staging API；staging API 连接现有本地 Docker PostgreSQL。
- 原因：当前 production API 采用生产身份模式，不接受开发 demo 身份头；直接修改生产容器或生产配置会扩大风险。临时 staging API 可以验证真实持久化、权限、审批和审计，同时保持生产容器不变。
- 边界：该验收证明的是本地 synthetic 环境闭环，不代表生产身份、生产部署、真实外部系统或生产数据验收完成。临时 staging 容器只用于运行期间，停止后不作为长期资产提交。
